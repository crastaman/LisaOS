# ntfy Notification Specification

**Status:** IMPLEMENTED (Phase C3) — `advisors/notify.py`,
`tests/test_notify.py` (22/22 passing). See
`docs/LISAOS/CONSOLE/examples/sample_notification_payload.json` and
`sample_notification_payload_degraded.json` (both real — generated by the
actual `build_payload()` code).

## Notification channel only

`advisors/notify.py` has **zero imports of `core/` or `engines/`**
(confirmed by grep, same standard as `advisors/gpt_advisor.py` and
`advisors/openai_client.py`). It cannot execute, approve, reject,
schedule, or trigger anything. Tapping a notification opens the Console
(Phase C4) at a deep link; **the Console, not the notification, is the
authoritative source of truth** for brief availability and decisions —
the notification is a pointer, nothing more.

## Payload allowlist (the core security property)

`build_payload(brief, *, base_url=None) -> dict` constructs the outbound
payload from exactly seven named keys, assigned one-by-one from six named
brief fields. It never does `payload.update(brief)` or any wholesale
copy, so nothing else on an Executive Brief — or anything from the
Decision Bundle the brief was generated from — can reach the wire:

| Payload field | Source | Notes |
|---|---|---|
| `brief_id` | `brief["brief_id"]` | |
| `headline` | `brief["headline"]`, truncated to 140 chars | falls back to a fixed safe string if missing/empty |
| `recommendation_summary` | derived from `brief["recommendation"]` | e.g. `"Recommendation: approve"`, or a fixed degraded-mode string — never the free-text `summary` field |
| `confidence` | `brief["confidence"]` | `null` for a degraded brief |
| `priority` | computed from `recommendation`, `escalation_recommendation.level`, `key_risks` (non-empty check only) | only the resulting label (`min`\|`low`\|`default`\|`high`\|`urgent`) crosses the boundary — the risk detail itself never does |
| `timestamp` | generated at send time | ISO 8601 UTC |
| `console_deep_link` | `f"{LISA_CONSOLE_BASE_URL}/brief/{brief_id}"`, or `null` if unset | only resolvable on the tailnet once Phase C4 exists |

**Explicitly never read into the payload**: `summary`, `key_risks`
content, `suggested_actions`, `missing_information`, `bundle_id`,
`bundle_schema`, `model`, `degraded_reason`, or anything from the source
Decision Bundle (evidence, `participating_workers`, `proposed_actions`,
governance data, file paths). `tests/test_notify.py
::TestBuildPayloadAllowlist.test_forbidden_content_never_reaches_payload_
even_when_present_on_brief` proves this by planting sentinel strings
(fake secrets, paths, customer data, transcript markers) in every
non-allowed field of a brief and asserting none of them appear anywhere
in the serialized payload.

Note on `headline`/`recommendation_summary`: both are informed by the
Decision Bundle (that is their entire purpose — a useless notification
would defeat the point) but are exactly the two fields the approved
requirements explicitly allow. The constraint this spec enforces is
about **payload field composition** — no raw/structured bundle data, no
evidence, no logs, no paths, no secrets — not "zero bundle influence,"
which would make a useful notification impossible.

## Delivery (`advisors/notify.py:send_notification()`)

- **Retry with bounded backoff**: up to `max_attempts` (default 3)
  attempts, sleeping `backoff_seconds * attempt` (default 0.5s, 1.0s)
  between failures — never an unbounded retry storm.
- **Timeout handling**: `timeout_seconds` (default 10) passed to the
  underlying `urlopen()` call; a timeout is categorized `"timeout"`.
- **Unreachable server handling**: connection refused / DNS failure /
  5xx → `"unavailable"`; 429 → `"rate_limited"`; any other 4xx or an
  unparseable response → `"invalid_response"`.
- **Duplicate suppression**: a persisted marker file at
  `reports/console/notifications/<brief_id>.json`, written only on
  confirmed successful delivery. A second `send_notification()` call for
  the same `brief_id` short-circuits before any network attempt, returns
  `status: "duplicate_suppressed"`, and is itself audit-logged. A
  *failed* send leaves no marker, so a later retry (a fresh
  `send_notification()` call, not an internal retry) is not blocked by
  it.
- **Audit logging**: every outcome — sent, failed (including
  `not_configured`), or duplicate-suppressed — appends one line to
  `reports/console/audit.jsonl` (the same file Phase C1/C2 reserved for
  this; C3 is the first module to actually write to it). Example lines:
  ```json
  {"event": "ntfy_sent", "brief_id": "eb-...", "at": "...", "priority": "high", "attempt": 1}
  {"event": "ntfy_failed", "brief_id": "eb-...", "at": "...", "category": "unavailable", "reason": "ntfy unavailable (503): ...", "attempts": 3}
  {"event": "ntfy_duplicate_suppressed", "brief_id": "eb-...", "at": "..."}
  ```

## Configuration

| Env var | Required | Purpose |
|---|---|---|
| `LISA_CONSOLE_NTFY_TOPIC` | Yes (else `not_configured`, fails closed with no network attempt) | the ntfy topic to publish to |
| `LISA_CONSOLE_NTFY_TOKEN` | No | ntfy access token, sent only as `Authorization: Bearer ...` |
| `LISA_CONSOLE_NTFY_SERVER` | No, defaults to `https://ntfy.sh` | **the entire provider abstraction** — point this at a self-hosted ntfy instance and nothing else changes |
| `LISA_CONSOLE_BASE_URL` | No | Console base URL for the deep link; omitted from the payload if unset |

### Provider abstraction

Deliberately minimal, not a plugin framework (matches the "no unnecessary
tool complexity" governance rule for a single current provider): all
ntfy-protocol-specific logic — the request shape, headers, and HTTP
semantics — lives in exactly one function, `_send_once()`. Payload
construction, retry, duplicate suppression, and audit logging are all
provider-agnostic and call `_send_once` only through the injectable
`publish_fn` parameter. Migrating to a self-hosted ntfy instance is a
`LISA_CONSOLE_NTFY_SERVER` config change; migrating to a different push
provider entirely means replacing `_send_once` (and nothing else).

## Failure handling

- **ntfy unavailable never blocks brief generation** — `advisors/notify.py`
  is fully decoupled from `advisors/gpt_advisor.py`: nothing in Phase C1
  or C2 calls this module, and this module never calls back into them.
  A brief is complete and usable the moment `write_brief()` (Phase C2)
  returns, regardless of what `send_notification()` does afterward.
- **Delivery failure is recorded in audit only** — `send_notification()`
  never raises for a delivery failure or missing configuration; it
  always returns a `NotificationResult` and always audit-logs the
  outcome. There is no code path where a notification problem propagates
  as an exception to a caller.
- **Console remains the authoritative source of truth** — nothing about
  notification delivery success or failure is recorded on the bundle or
  brief itself; a Console (Phase C4) listing pending approvals would
  read directly from `reports/console/bundles/`, entirely independent of
  whether any notification about them was ever sent.

## Trigger

Not wired to any automatic pipeline in Phase C3 — `send_notification()`
takes an already-generated Executive Brief dict and is called
independently, matching Phase C1/C2's on-demand-only stance (no
orchestrator exists yet that would call bundle export → brief generation
→ notification in one sequence; that wiring, if wanted, is a later
phase's decision, not assumed here).
